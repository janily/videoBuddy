## 0. 一句话结论

**左边的画布就是“正在成形的这支视频”，右边的助手负责把用户一步步带到“生成”。**

用户只需要做三件事：**说清楚想做什么 → 选一个画风 → 点生成**。其余工作（整理需求、推荐画风、写脚本、拆镜头、画画面、配乐）都由系统完成，并且每一步都**实时出现在画布上**。全程不使用弹窗。

---

## 1. 第一性原理：小白用户到底需要什么

### 1.1 用户是谁

- 第一次做视频，不懂“脚本、分镜、画风、比例”这些词。
- 脑子里只有一个模糊念头：“给咖啡店做个介绍”“中秋给家人发个祝福”。
- 耐心有限：等待超过十几秒、看不到任何变化，就会觉得“坏了”。

### 1.2 用户真正要的结果

一支**看得懂、像样、能直接发出去**的短视频。过程中只关心三个问题：

1. **它理解我了吗？**（我说的话被正确接住了吗）
2. **它会做成什么样？**（画风、内容、节奏）
3. **还要多久，现在在干什么？**

### 1.3 推导出的设计约束

| 第一性事实 | 推导出的约束 |
|---|---|
| 小白不会填表，只会聊天 | 唯一的输入方式是聊天；画布上的操作只是“快捷方式”，不能变成必填表单 |
| 小白看不懂抽象描述 | 凡是能“看见”的都要“给看”：理解的要点、画风样片、脚本、镜头、进度 |
| 决策越多越容易放弃 | 必须由用户做的决定只有 2 个：选画风、点生成。其余都要有合理默认值 |
| 生成要几分钟 | 等待必须“可见且有意义”：每完成一步，画布上就多出一样真实的东西 |
| 弹窗会打断思路、遮住上下文 | 不用弹窗。所有选择都在画布原位完成，聊天始终可见 |
| 用户随时会改主意 | 任何阶段都能用聊天改；画布要清楚标出“这块因为你刚才的话变了” |

| # | 现状 | 位置 | 对小白的影响 |
|---|---|---|---|
| D1 | 左侧按 5 个互斥状态整屏切换（欢迎 / 想法渐清 / 生成中 / 效果确认 / 成片），每次切换整页替换 | `result-stage.tsx` | 用户看不到“积累”，感觉不到视频在一步步成形 |

| D9 | 画布上的偏好（时长、比例）无法直接改，只能在聊天里说 | — | 小白不知道可以改，也不知道该怎么说 |

## 3. 设计原则（研发评审时的判据）

1. **画布是活的视频档案，不是页面状态机。** 画布从上到下按创作顺序排列固定的几个“卡片”，内容随对话逐步填满。之前的内容不消失。
2. **聊天推进，画布呈现。** 助手每做一件事（理解了一点、推荐了画风、写好了脚本），画布上都要有对应的变化，并在聊天里用一句话指向它。
3. **一次只要一个决定。** 任何时刻，画布上最多只有一个“需要你决定”的高亮区域。
4. **原位操作，零弹窗。** 选择、确认、修改都在卡片内完成。需要更多空间时就地展开，不浮层遮挡。
5. **每 3–10 秒必须有可见变化。** 生成阶段按真实步骤推进：脚本出现 → 镜头逐个出现草图 → 逐个变成可播放片段 → 成片。
6. **默认值优先，可改但不必改。** 时长、比例、配乐都有默认值，并在画布上显示为可点的“小标签”，不显示为表单。
7. **用户的话永远优先。** 画布上的任何点击，都等价于在聊天里说了一句话，并在聊天里留下记录，保证对话是唯一的事实来源。

## 4. 信息架构与布局

### 4.1 桌面端（≥ 960px）

```
┌───────────────────────────────────────────────┬─────────────────────────┐
│ VideoBuddy  中秋团圆祝福 ▾          我的视频  + 新建 │                         │
├───────────────────────────────────────────────┤   视频助手               │
│  进度条：① 想法 ─ ② 画风 ─ ③ 脚本 ─ ④ 生成 ─ ⑤ 成片   │                         │
│                                               │   （对话流）              │
│ ┌─ ① 想法卡 ───────────────────────────────┐   │                         │
│ │ 主题 / 给谁看 / 想达到什么 / 必须出现的内容      │   │                         │
│ │ [30秒] [竖屏] [自动配乐]   ← 可点的小标签       │   │                         │
│ └─────────────────────────────────────────┘   │                         │
│ ┌─ ② 画风卡 ───────────────────────────────┐   │   快捷回复 chips         │
│ │ 推荐 3 个（样片+一句理由）  [看更多画风 ▸]      │   │   ┌───────────────────┐ │
│ └─────────────────────────────────────────┘   │   │ 输入框             │ │
│ ┌─ ③ 脚本卡（分镜）──────────────────────────┐   │   └───────────────────┘ │
│ │ 镜头1 … 镜头N（文字 → 草图 → 可播放）          │   │                         │
│ └─────────────────────────────────────────┘   │                         │
│ ┌─ ④/⑤ 成片卡 ─────────────────────────────┐   │                         │
│ │ 生成按钮 / 生成进度 / 播放器 + 下载 + 调整       │   │                         │
│ └─────────────────────────────────────────┘   │                         │
└───────────────────────────────────────────────┴─────────────────────────┘
```

- 画布是一个可滚动的单列，最大内容宽度沿用 `--vb-content`。
- **当前需要用户关注的卡片自动滚动到视口内**，并有一次轻微高亮（200ms 描边渐显），之后保持 `aria-current`。
- 已完成的卡片折叠为一行摘要，可点开。未到达的卡片显示为占位（灰色标题 + 一句“聊完想法后，这里会出现…”），让用户知道接下来会发生什么。

### 4.2 移动端（< 960px）

- 保留“聊想法 / 看视频”两个页签，“看视频”改名为 **“画布”**。
- 画布有新变化时，“画布”页签显示**小红点 + 变化摘要气泡**（例如“画风推荐好了”），点击切过去并滚动到对应卡片。
- 聊天里每条“指向画布”的助手消息，带一个“在画布上看 ›”按钮。
- 生成中，聊天页顶部显示一条**常驻迷你进度条**（第几步 / 共几步），点击跳到画布。

## 5. 用户旅程与状态机

### 5.1 阶段定义

阶段由数据推导，**不新增后端 phase 字段**，前端用以下规则计算（伪代码见 §9.3）：

| 阶段 | 进入条件 | 画布焦点 | 助手的目标 |
|---|---|---|---|
| S0 开场 | 无项目或无用户消息 | 欢迎区 + 示例 | 让用户说出第一句话 |
| S1 理清想法 | 有消息，`subject` 为空或缺关键信息 | ① 想法卡 | 每轮只问一个问题，补齐“主题、给谁看、目的” |
| S2 选画风 | 想法基本完整，`styleSlug` 为空 | ② 画风卡 | 推荐 3 个画风并说明理由，引导用户在画布上点选 |
| S3 看脚本 | 有画风，脚本草稿已生成且与当前想法版本一致 | ③ 脚本卡 | 用一两句话讲清故事走向，问“这样可以吗，要不要改哪一镜” |
| S4 生成中 | `activeProduction` 存在 | ③ 脚本卡逐镜点亮 + ④ 进度 | 告诉用户正在做什么、预计多久；接收修改意见并标为“下一版” |
| S5 成片 | 有 `currentResult` 且无进行中任务 | ⑤ 成片卡 | 引导下载，或提出一处具体可改的点 |
| S6 修改 | 成片后想法版本又变了 | 被影响的卡片标“已更新” + ⑤ 出现“按新想法重新生成” | 讲清改了什么、会影响哪几镜 |

> 说明：S3 是本方案新增的**轻量检查点**，不是旧流程里的“预览 → 确认”。生成脚本只需 1 次模型调用、几秒钟，却能让用户在最贵的步骤（画面和渲染）之前看到“讲什么、怎么讲”。用户不必确认，直接点“生成”即可；生成时会**复用这份脚本**，不会重新写一遍。

### 5.2 状态流转图

```
S0 ──说第一句话──▶ S1 ──想法够了──▶ S2 ──选定画风──▶ S3 ──点“生成”──▶ S4 ──完成──▶ S5
                    ▲                ▲               │                   │              │
                    └────聊天改想法──┴───────────────┴───────────────────┘              │
                                                              S6 ◀──聊天改想法/换画风───┘
```

- 任何阶段，用户在聊天里改了想法，都会回到相应阶段，但**不清空**后面的卡片，只把它们标为“需要更新”。
- 用户可以跳步：S1 时直接说“用水墨风，30 秒，直接做”，系统应一次填好 ①②，生成脚本后停在 S3 并提示可以生成。用户也可以在 S2/S3 直接点“生成”，前提是 ① 有主题、② 有画风。

### 5.3 必须由用户做的决定

| 决定 | 位置 | 默认值 / 兜底 |
|---|---|---|
| 选画风 | ② 画风卡 | 不设自动默认值。助手推荐首选，并在卡片上标“推荐”；用户说“你定吧”时，助手直接写入首选 |
| 点生成 | ③ 脚本卡底部 / ⑤ 成片卡 | 无。生成会花钱和时间，必须由用户触发 |

其他（时长、比例、配乐）都有默认值，显示为可点标签，不打断流程。

## 6. 画布卡片规格

每张卡片统一结构：**标题行（序号 + 名称 + 状态徽标）→ 内容区 → 卡片内操作区**。

状态徽标取值：`待开始`（灰）、`进行中`（绿色点 + 动效）、`需要你选`（强调色）、`已完成`（勾）、`已更新`（蓝点，5 秒后淡出为已完成）、`需要更新`（黄）。

### 6.1 ① 想法卡（Brief）

**目的**：让用户一眼看到“它理解了什么、还缺什么”。

| 字段 | 来源 | 展示 |
|---|---|---|
| 主题 | `understanding.subject` | 大号一行；为空时显示“还没说”占位 |
| 给谁看 | `understanding.audience` | 小号；缺失时显示虚线占位“给谁看？” |
| 想达到什么 | `understanding.objective` | 同上 |
| 要点 | `understanding.summary`（≤3 条） | 列表 |
| 必须出现的信息 | `understanding.facts` 中 `critical/mustInclude` 的条目 | 带来源小图标的标签（来自聊天 / 来自资料） |
| 规格标签 | `preferences.durationSec / aspect`，配乐取自 `quick.music` | `[30 秒 ▾] [竖屏 ▾] [自动配乐 ▾]` |

交互：

- **虚线占位可点**：点“给谁看？”→ 在聊天输入框预填“这个视频主要给 ___ 看”，光标停在空白处。不弹窗，也不在画布里加输入框，保持“聊天是唯一输入”。
- **规格标签就地展开**：点 `[30 秒 ▾]` 在标签下方展开一行分段选择 `20 / 25 / 30 秒`，点选即生效。
  - 生效方式：前端发送一条**系统代发的用户消息**（如“时长改成 25 秒”，在聊天里以“通过画布设置”的小标注显示），由助手写入偏好。这样保持对话是唯一事实来源，见原则 7。
  - 可选的后续优化：新增“偏好直写”接口，跳过模型调用，见 §10.2 P2。
- 字段被助手更新时，对应行显示 `已更新` 徽标，并做一次 600ms 的背景淡入高亮。

空状态（S0）：卡片不显示，画布显示欢迎区（沿用现有欢迎文案和三个示例）。

### 6.2 ② 画风卡（Style）——替代画风弹窗

**目的**：用“看得见的样子”代替“画风名词”，在画布原位完成选择。

布局：

```
② 画风   [需要你选]
根据「中秋给家人的祝福，温暖、有月亮」推荐：
┌────────────┐ ┌────────────┐ ┌────────────┐
│  样片/动图  │ │  样片/动图  │ │  样片/动图  │
│ 纸雕灯影 ★推荐│ │ 红色窗花剪纸 │ │ 中国水墨    │
│ 温暖的夜景，  │ │ 喜庆吉祥，   │ │ 写意留白，   │
│ 灯光透过纸层 │ │ 适合节日问候 │ │ 适合诗意表达 │
│  [用这个]   │ │  [用这个]   │ │  [用这个]   │
└────────────┘ └────────────┘ └────────────┘
[看更多画风 ▸]（就地展开，不弹窗）
```

- **推荐来源**（按优先级）：
  1. 助手本轮输出的 `recommendations`（新结构，见 §8.2），含理由文案；
  2. 前端用 `recommendStyles(hint)` 做的本地推荐（已有，见 `styles/recommendations.ts`），理由取 `styleFits[id].goodFor`。
- **样片**：`public/style-samples/<id>.jpg`；同目录下有 `<id>.mp4` 时，鼠标悬停 / 进入视口后静音循环播放（`preload="none"`，进入视口才加载）。没有样片时显示该风格的主色块 + 名称，**不得留空白方框**。
- **“看更多画风”**：在卡片内**向下展开**一个分组浏览区：按分类分组，每组横向滚动；顶部一个搜索框，支持按名称或用途搜（复用已有的按用途匹配逻辑）。展开区最大高度 60vh，内部滚动。再次点击收起。
- **选择**：点“用这个”→ 卡片立即进入 `已完成`，折叠为一行“画风：纸雕灯影 [换一个]”；同时聊天里出现一条代发消息“画风用「纸雕灯影」”，助手确认并进入下一步。
- **已选状态下换画风**：点“换一个”重新展开推荐区；若已有脚本或成片，在按钮旁提示“换画风会重新画所有镜头”。

触发时机：

- 助手判断想法“够用了”（主题非空，且受众或目的至少有一项，或用户已明确表示“就这些”）→ 输出推荐 → 画风卡从占位变为 `需要你选`，并自动滚动到视口。
- 用户在 S1 主动说画风名称或描述风格（“想要可爱一点的”）→ 也会触发推荐。

### 6.3 ③ 脚本卡（Storyboard）

**目的**：让用户在花时间、花钱之前看到“讲什么、怎么讲”，生成时再在同一张卡上看到每一镜逐步成形。

脚本卡的每一镜有四种显示状态，同一张卡片从头用到尾：

| 状态 | 何时 | 一镜显示 |
|---|---|---|
| 文字 | 脚本草稿已生成（S3） | 序号、时长（如 0:00–0:07）、这一镜要表达的一句话（`scriptLine`）、画面描述（`visualIntent`，灰色小字） |
| 画中 | S4，该镜视觉源码生成中 | 骨架闪烁 + “正在画…” |
| 草图 | 该镜源码已生成、渲染未完成 | 一张静态预览帧（见 §10.2 后端 B4） |
| 可播放 | 该镜渲染完成 | 缩略图，点击后在卡内就地播放该镜片段 |

卡片顶部显示一句故事梗概（`treatment.summary`），以及“为什么这样讲”（`selectionReason`，可展开）。

卡片内操作：

- 每镜悬停时显示 **“改这一镜”**：在聊天输入框预填“第 3 镜改成：”。不在画布内编辑文本，以免出现两套编辑入口。
- 成片后每镜显示 **“重画这一镜”**，复用已有的 `/quick` 接口 `redoShotId`。
- 底部主按钮：**“生成视频 →”**，旁边一行小字“约 3–5 分钟，会依次画出每个镜头”。

脚本草稿的生成：

- 何时生成：画风确定、想法版本更新后，由系统自动触发“只写脚本”的轻任务（见 §10.2 B1）。用户不需要点任何按钮。
- 想法又变了：旧脚本标 `需要更新`、灰化，自动重写；聊天里助手说明“我按你刚才说的调整了第 2、3 镜”（由前后两版脚本对比得出）。

### 6.4 ④ 生成进度（嵌在脚本卡与成片卡之间）

```
正在生成 · 第 2 步 / 共 5 步 · 约还需 2 分钟
●构思  ●画镜头 3/5  ○渲染  ○拼接  ○配乐
[停止生成]
```

- 5 个步骤与 `quick/film.ts` 的 stage 一一对应：`treatment / visual / picture / composition / music`。
- “画镜头 3/5”“渲染 2/5”使用 `activity.updated` 事件里已有的 `completed / total` 字段（当前未填，需要后端填上，见 B3）。
- 预计剩余时间：按前端经验值（每镜画约 25 秒、渲染约 15 秒、拼接加配乐约 20 秒）× 剩余量粗估，显示为“约还需 X 分钟”，**只取整到分钟**，永不显示精确秒数。
- 停止：调用已有的取消接口，用确认态替代弹窗：按钮第一次点击变成“确定停止？已画好的镜头会保留”（3 秒内再点一次确认），3 秒后自动复原。
- 生成中用户在聊天里提修改：助手回复“记下了，会在下一版里改”，脚本卡对应镜头旁显示小标签“下一版会改”（数据来自 `pendingInputs`）。

### 6.5 ⑤ 成片卡（Result）

- 播放器按比例显示（竖屏视频与右侧信息左右并排，已实现，见 `portrait-layout`）。
- 主按钮“下载视频”；次要信息一行：画风 · 时长 · 比例 · 配乐 · 含 AI 生成标识。
- **配乐**：就地下拉选择（已实现），显示授权信息。
- **版本**：“上一个版本”以横向缩略图条的形式显示在播放器下方（替代当前藏在“更多”里的历史），点击就地切换播放，并提供“恢复这个版本”。
- **下一步引导**（只显示一个）：
  - 第一次成片：显示“满意就下载；想改哪里，在右边直接说，比如‘第 2 镜的月亮再大一点’”；
  - 想法版本比成片新：显示主按钮“按新想法重新生成”，并列出将变化的镜头。

### 6.6 “我的视频”（替代弹窗）

- 顶栏的“我的视频”改为**顶栏下拉面板**：在顶栏下方展开，宽 360px，不遮罩、不锁滚动，点外部或按 Esc 收起。最多显示 8 个最近项目，带缩略图和阶段。
- 底部链接“查看全部 ›”跳转到独立页 `/video/projects`（新页，复用 `lookup` 接口）。

## 7. 画布与聊天的联动规则

| 触发 | 画布反应 | 聊天反应 |
|---|---|---|
| 助手更新了想法（`understanding.updated`） | ① 对应字段 `已更新` 高亮 | 回复里用一句话说明更新了什么 |
| 助手给出画风推荐 | ② 进入 `需要你选`，自动滚动到视口 | 回复末尾附一句“我在左边放了 3 个画风，点一个就行”；移动端附“在画布上看 ›” |
| 用户在画布上选画风 / 改规格 | 卡片即时更新（乐观更新，失败回滚） | 插入一条代发用户消息（带“通过画布”标注），助手接着回复 |
| 脚本草稿写好 | ③ 从占位变为文字分镜 | 助手用两句话讲故事走向，并问“要改哪一镜吗？没问题就点生成” |
| 生成中每一步完成 | ③ 对应镜头状态推进，④ 进度前进 | 不刷屏：只在“开始生成”和“生成完成 / 失败”时各发一条 |
| 成片完成 | ⑤ 出现播放器并自动滚动；移动端画布页签出现红点 | 助手说完成了，并给出**一个**可改的建议 |
| 失败 | 出错步骤标红并给出原因，主按钮变“重试” | 助手用人话解释，告诉用户“已画好的镜头都保留了” |

**引用约定**：助手回复中提到某张卡片或某一镜时，前端渲染为可点链接（如「第 3 镜」「画风」）。点击后画布滚动到对应位置并高亮 1.5 秒。实现方式：助手结构化输出里带 `canvasRefs`（见 §8.2），前端把对应文本片段替换为链接。

**代发消息**：画布操作产生的消息仍走 `POST /messages`，文本由前端模板生成，并附带 `origin:'canvas'`（新增字段，仅用于展示标注）。服务端照常交给助手处理，保证助手对所有变化都“知情”。

## 8. 视频助手（Agent）行为规范

### 8.1 对话节奏

1. **每轮最多问一个问题**，并附 2–4 个**快捷回复**（chips），让小白点选即可回答。
2. **先复述再提问**：“记下了：中秋、给家人、温暖。还想确认一下，视频主要发在哪里？”
3. **问题的优先级**：主题 > 给谁看 > 想达到什么 > 必须出现的信息（名字、日期、地点）> 时长/比例。后两项有默认值，**不主动问**，除非用户提到发布平台（这时建议竖屏）。
4. **引导选画风的时机**：主题已明确，且受众或目的至少有一项明确，或者用户已经回答过 2 轮问题。到时机后不再追问细节，直接推荐画风。
5. **引导生成的时机**：画风已选且脚本草稿就绪 → 讲故事走向，并说“没问题就点左边的‘生成视频’”。**助手不能替用户点生成。**
6. **用户说“你定吧 / 随便 / 直接做”**：助手采用推荐首选和全部默认值，写入后说明“我先按纸雕灯影、30 秒竖屏来，脚本在左边，点生成就开始”。
7. **字数**：每条回复 ≤ 80 个汉字（不含快捷回复），不用 Markdown 标题和列表。

### 8.2 结构化输出（扩展 `GuidanceDecisionSchema`）

在现有字段基础上新增以下**可选**字段，旧字段保持兼容：

```ts
// src/mastra/video/director.ts —— 新增字段（均为 optional）
quickReplies?: Array<{ label: string; text: string }>;  // ≤4，label≤8字，点击即发送 text
recommendations?: Array<{                               // 画风推荐，2~3 个
  styleId: string;    // 必须是 styleCatalog 中的 id（guardGuidance 校验）
  reason: string;     // ≤30字，面向小白的一句话理由
  primary: boolean;   // 恰好一个 true
}>;
canvasFocus?: 'brief' | 'style' | 'script' | 'result';  // 本轮希望画布聚焦的卡片
canvasRefs?: Array<{ text: string; target: 'brief'|'style'|'script'|'result'; shotId?: string }>;
// text 必须是 reply 中出现的原文片段，前端据此生成链接
readiness?: { brief: 'missing'|'partial'|'enough'; nextStep: 'ask'|'choose_style'|'review_script'|'generate'|'done' };
```

服务端校验（加在 `guardGuidance`）：

- `recommendations` 的 `styleId` 都在目录里、互不重复，并且恰好一个 `primary`；同时把 `recommendedStyleId` 设为 `primary` 那一项（兼容旧字段）。
- `canvasRefs[].text` 必须是 `reply` 的子串，否则丢弃该项，不报错。
- `quickReplies` 数量 ≤ 4，`label` ≤ 8 字，`text` ≤ 60 字，超限的项丢弃。
- 新字段不合法时**只丢弃该字段**，不让整轮失败（这些字段只影响呈现）。

持久化：把 `quickReplies / recommendations / canvasFocus / canvasRefs` 随助手消息一起归档（`ArchivedMessage` 新增可选字段 `ui`），刷新页面后可以复现。

### 8.3 提示词要点（追加到 `directorInstructions`）

- 明确告诉模型：用户是第一次做视频的普通人；左边画布会显示你整理的想法、推荐的画风和脚本；你的回复要**指向画布**，不要在聊天里重复长内容。
- 写明 §8.1 的节奏规则和时机判定，以及 `readiness` 字段的填写标准。
- 推荐画风时只看 `styleCatalog` 的 `goodFor / mood / look`，理由用用户能懂的话（“温暖的夜景，灯光透过纸层”），**不说专业术语**。
- 禁止输出：Markdown 标题、超过 4 个选项的列表、“先看效果 / 确认制作”等旧流程用语。

### 9.3 阶段计算（伪代码）

```ts
function deriveStage(v: ProjectView, draft: ScriptDraft | null): Stage {
  if (!v || v.messages.length === 0) return 'S0';
  if (v.activeProduction) return 'S4';
  const briefReady = v.understanding.subject.trim() !== '' && (hasAudience(v) || hasObjective(v) || userSaidEnough(v));
  if (v.currentResult) return draftIsNewer(v, draft) ? 'S6' : 'S5';
  if (!briefReady) return 'S1';
  if (!v.preferences.styleSlug) return 'S2';
  return 'S3'; // 脚本草稿生成中时，S3 内显示骨架
}
```

> `hasAudience / hasObjective` 依赖 `understanding.audience / objective` 进入 `ProjectView`（目前 view 只暴露 `summary` 和 `subject`，见后端 B6）。

### 9.4 无弹窗清单（验收时逐项检查）

| 原交互 | 新交互 |

| 上传资料的授权勾选 | 保持行内（已是行内） |

全站除浏览器原生文件选择器外，**不允许出现 `<dialog>`、遮罩层、`window.confirm/alert`**。在 E2E 中加断言：`page.locator('dialog[open]')` 数量始终为 0。

### 9.5 可访问性

## 12. 埋点与成功指标

| 指标 | 定义 | 目标（首月） |
|---|---|---|
| 首片完成率 | 新项目中，24 小时内得到第一支成片的比例 | ≥ 45% |
| 首片耗时 | 从第一条消息到第一支成片的中位时间 | ≤ 8 分钟 |
| 到达生成的对话轮数 | 点“生成视频”前用户发的消息数（中位数） | ≤ 4 |
| 画风推荐采纳率 | 选中的画风来自推荐 3 个的比例 | ≥ 70% |

## 15. 风险与待决问题

| # | 问题 | 建议 |
|---|---|---|
| R1 | 自动写脚本会增加模型调用（每次想法变化都写一次） | 防抖：想法版本稳定 3 秒后再入队；同一版本只写一次；生成时复用，因此总调用量不增加 |
| R2 | 草图帧需要额外渲染，可能拖慢整体生成 | 草图与正式渲染共用同一个容器（先出单帧，再出整镜），或者草图只用于前 2 镜 |
| R3 | 模型可能不按约定输出 `recommendations` / `canvasRefs` | 字段级容错（不合法即丢弃），前端用本地 `recommendStyles` 兜底 |
| R4 | 画布操作代发消息会让聊天变长 | 代发消息使用紧凑样式（单行、浅色、带“通过画布”标注），助手对这类消息只做一句确认 |
| R5 | 43 种画风的样片质量参差 | B10 先批量生成，由运营人工挑选；没有通过挑选的画风在推荐中降权 |
| Q1 | 是否允许用户在画布上直接编辑脚本文字？ | 本期不做（避免出现两个编辑入口），统一走聊天；M3 之后根据埋点再评估 |
| Q2 | 30 秒以上时长、旁白何时开放？ | 不在本期范围，规格标签只提供 20/25/30 秒 |
